# Enterprise Spec — ADR (Architecture Decision Record) 포맷

> 조직 전체 아키텍처 결정을 **왜** 그렇게 결정했는지 기록하고 보존하는 표준을 정의한다.  
> 코드는 **무엇**을 하는지 보여주지만, ADR은 **왜** 그 선택을 했는지를 미래 팀원에게 전달한다.  
> ARB(Architecture Review Board) 검토가 필요한 결정은 반드시 ADR로 기록한다.

---

## Enterprise ADR 적용 범위

| ADR 필수 | ADR 권장 | ADR 불필요 |
|---------|---------|----------|
| 전사 기술 스택 변경 | 서비스 내 주요 라이브러리 선택 | 코드 스타일·포매팅 |
| 플랫폼 아키텍처 결정 | 새 외부 서비스 도입 | 버그 수정 |
| 보안 정책 변경 | 성능 최적화 전략 | 문서 수정 |
| 데이터 모델 Breaking Change | DB 인덱스 추가 | 테스트 추가 |
| LLM 모델·공급사 변경 | 배포 방식 변경 | — |

---

## ARB(Architecture Review Board) 연동

| 결정 규모 | 프로세스 |
|---------|---------|
| 팀 내부 결정 | ADR 작성 → 팀 리뷰 → 수락 |
| 플랫폼·전사 영향 | ADR 초안 → ARB 리뷰 미팅 → 수락·조건부 수락·반려 |
| 긴급 결정 | ADR 작성(사후) → 2영업일 내 ARB 통보 |

## 상태 정의

| 상태 | 의미 | 처리 |
|------|------|------|
| `제안됨` | 논의 중 — 아직 결정되지 않음 | ARB 미팅 대기 또는 팀 리뷰 중 |
| `수락됨` | 팀·ARB 합의 완료 — 현재 유효한 결정 | 구현 가능 |
| `폐기됨` | 더 이상 적용하지 않음 (대체 ADR 없음) | 이유 기록 필수 |
| `대체됨` | 다른 ADR로 교체됨 | 대체 ADR 번호 링크 필수 |

## 섹션별 작성 가이드

### 배경 작성 팁
- 미래 독자(1~3년 후 합류한 팀원)가 당시 상황을 이해할 수 있도록 충분한 컨텍스트 제공
- "당연한" 제약도 명시 (팀 규모, 예산, 기간, 기술 성숙도 등)
- 비즈니스 배경도 포함 (왜 지금 이 결정이 필요한가)

### 검토한 옵션 작성 팁
- 최소 2개 이상 옵션 기술 (선택지가 없었다면 의사결정이 아님)
- 선택하지 않은 이유를 솔직하게 기술
- 각 옵션의 장단점은 측정 가능한 수치로 (가능하면)

### 결과 작성 팁
- 부정적 결과를 회피하지 않고 솔직하게 기록
- 트레이드오프를 인정하는 것이 좋은 ADR
- 모니터링해야 할 리스크와 담당자 명시

---

## 예시 ADR

```markdown
# ADR-0004: 전사 이벤트 브로커로 Apache Kafka 선택

## 상태
수락됨

## 날짜
2026-05-03

## 결정자
Platform Engineering Team  
ARB 검토: 필요 (전사 영향)

---

## 배경

마이크로서비스 간 비동기 통신이 필요해졌다.
현재 REST 동기 호출로는 LLM 처리(~30초) 동안 HTTP 연결을 유지해야 하며,
외부 API 장애 시 메시지가 유실된다.
팀 규모: 5개 서비스팀. 일 예상 메시지: ~10만건.

---

## 검토한 옵션

### 옵션 1 — RabbitMQ
- 장점: 설정 간단, RPC 패턴 지원
- 단점: 메시지 보존 어려움, 재처리 복잡, 대용량 부적합

### 옵션 2 — Redis Streams
- 장점: 이미 Redis 사용 중, 추가 인프라 불필요
- 단점: Kafka 대비 기능 제한, 클러스터 운영 복잡

### 옵션 3 — Apache Kafka (선택)
- 장점: 메시지 보존·재처리, 대용량, Schema Registry, 생태계 풍부
- 단점: 운영 복잡도 높음, 러닝 커브

---

## 결정

Apache Kafka를 선택한다.
왜냐하면 메시지 보존·재처리 기능이 데이터 파이프라인과 LLM 비동기 처리에 필수이며,
장기적으로 Schema Registry를 통한 이벤트 계약 관리가 가능하기 때문이다.

---

## 결과

### 긍정적 결과
- 메시지 유실 없음 (보존 기간 내 재처리 가능)
- 데이터 파이프라인과 애플리케이션 이벤트 통합 가능

### 부정적 결과 / 트레이드오프
- 운영 인프라 추가 (Platform 팀 관리 필요)
- Consumer Group 설계 학습 비용
```
