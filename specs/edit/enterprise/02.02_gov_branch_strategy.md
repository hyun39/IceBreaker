# Enterprise Spec — 브랜치 전략 (Branch Strategy)

> 조직 전체 코드 통합 흐름의 **개발 속도·안전성 균형**을 정의한다.  
> 핵심: Trunk-Based Development + Feature Flag로 지속적 통합을 실현한다.

---

## 전사 브랜치 모델 선택 기준

| 모델 | 특징 | 권장 상황 |
|------|------|----------|
| **Trunk-Based Development (TBD)** | `main` 단일 브랜치, 소규모 단기 PR, Feature Flag 필수 | 팀 규모 5명 이하, 배포 주기 일 단위 이상 |
| **GitHub Flow** | `main` + feature 브랜치, 빠른 PR·머지 | 단일 서비스 팀, 단순 릴리스 |
| **GitFlow (변형)** | `main` + `develop` + feature/release/hotfix | 복수 버전 동시 지원, 릴리스 주기 2주 이상 |

**전사 기본값**: GitHub Flow (단순) → 서비스 성숙 시 TBD로 전환.  
GitFlow는 레거시 서비스 유지보수만 허용.

---

## Trunk-Based Development (TBD) 표준

### 핵심 원칙

```
[개발자]
  └─ 매일 main에 소규모 커밋 또는 단기(1~2일) PR
  └─ 미완성 기능은 Feature Flag로 감춤 — main은 항상 배포 가능

main ──────────────────────────────────────► 항상 Green
  ↑               ↑              ↑
feature/a(1일)  feature/b(2일)  hotfix(수시간)
```

### Feature Flag 통합 (OpenFeature)

```python
# OpenFeature 표준 SDK — Python
from openfeature import api
from openfeature.provider.flagd import FlagdProvider

api.set_provider(FlagdProvider(host="flagd.internal", port=8013))
client = api.get_client("sp500-api")

# 기능 플래그 사용
@router.get("/api/v1/mart/trend-analysis")
async def get_trend(request: Request, token: TokenPayload = Depends(verify_token)):
    # 신기능은 Flag로 제어 — main에 머지했지만 선택적 노출
    use_v2_analysis = client.get_boolean_value(
        flag_key="mart-trend-v2",
        default_value=False,
        evaluation_context={"user_id": token.sub, "team": token.team},
    )
    if use_v2_analysis:
        return await mart_service.get_trend_v2(...)
    return await mart_service.get_trend_v1(...)
```

```yaml
# flagd 플래그 정의 (Git에서 관리)
flags:
  mart-trend-v2:
    state: ENABLED
    variants:
      "on": true
      "off": false
    defaultVariant: "off"
    targeting:
      if:
        - in: [["data-platform", "sre"], { var: team }]
        - "on"
        - "off"
```

**Feature Flag 수명주기**:

| 단계 | 설명 | 기한 |
|------|------|------|
| 도입 | 코드 머지, Flag OFF | 개발 완료 시 |
| 점진 노출 | 10% → 50% → 100% | 1~2주 |
| 정식 출시 | Flag 제거, 코드 정리 | 출시 후 1~2주 내 |

> **Flag Debt 금지**: 30일 이상 사용하지 않는 Flag는 자동 알림 → 제거 의무.

## Conventional Commits 표준

### 커밋 메시지 형식

```
<type>(<scope>): <description>

[body — 선택, 72자 이내 줄바꿈]

[footer — 선택]
BREAKING CHANGE: <설명>
Refs: #이슈번호
```

### 타입 목록

| 타입 | 의미 | 버전 영향 |
|------|------|---------|
| `feat` | 신기능 | minor ↑ |
| `fix` | 버그 수정 | patch ↑ |
| `perf` | 성능 개선 | patch ↑ |
| `refactor` | 리팩터링 (기능 변화 없음) | patch ↑ |
| `docs` | 문서만 변경 | — |
| `test` | 테스트 추가·수정 | — |
| `build` | 빌드·의존성 변경 | — |
| `ci` | CI 설정 변경 | — |
| `chore` | 기타 유지보수 | — |
| `BREAKING CHANGE` | 하위 호환 깨는 변경 (footer 또는 `!`) | major ↑ |

```bash
# 좋은 예시
feat(mart): Add bilingual trend analysis output (KO/EN)
fix(pipeline): Handle yfinance empty response for non-trading day
perf(ods): Index trade_date DESC to speed up date-range queries
feat!: Remove deprecated v0 API endpoints

BREAKING CHANGE: /api/v0/* endpoints have been removed.
Migrate to /api/v1/* endpoints.

# 나쁜 예시
fix: 수정
update: 코드 변경
작업 중
```

## 브랜치 보호 규칙 (GitHub Branch Protection)

```yaml
# 조직 수준 Ruleset — GitHub Organization Rules
rules:
  - name: "main 브랜치 보호"
    target: main
    enforcement: active
    conditions:
      repository_name: { include: ["**"] }
    rules:
      - type: pull_request
        parameters:
          required_approving_review_count: 1
          dismiss_stale_reviews_on_push: true
          require_code_owner_review: true         # CODEOWNERS 필수
          require_last_push_approval: true
      - type: required_status_checks
        parameters:
          strict_required_status_checks_policy: true
          required_status_checks:
            - { context: "lint", integration_type: "check_run" }
            - { context: "test-unit", integration_type: "check_run" }
            - { context: "security-scan", integration_type: "check_run" }
      - type: non_fast_forward          # Force push 금지
      - type: deletion                  # 브랜치 삭제 금지
      - type: commit_message_pattern
          pattern: "^(feat|fix|perf|refactor|docs|test|build|ci|chore)(\\(.+\\))?!?: .{1,72}"
```

## 멀티레포 vs 모노레포 기준

| 항목 | 모노레포 | 멀티레포 |
|------|---------|---------|
| 코드 공유 | 쉬움 (직접 import) | SDK 패키지 발행 필요 |
| 원자적 커밋 | 여러 서비스 동시 변경 가능 | 여러 PR 조율 필요 |
| CI 속도 | 증분 빌드(Turborepo) 없으면 느림 | 각 레포 독립 |
| 팀 자율성 | 낮음 (공유 설정) | 높음 |
| 적합 | 프론트엔드·Design System·공유 라이브러리 | 독립 마이크로서비스 |

**전사 권장**: 프론트엔드·공유 라이브러리 → 모노레포(Turborepo), 백엔드 서비스 → 멀티레포.

## PR 품질 기준

| 항목 | 기준 |
|------|------|
| PR 크기 | 400줄 이내 (diff 기준), 초과 시 분리 권고 |
| PR 유지 기간 | 3일 이내 리뷰 완료 (SLO) |
| Draft PR | WIP는 반드시 Draft 표시 |
| 머지 전략 | Squash merge 기본 (히스토리 정리), 릴리스는 Merge commit |
| 자동 삭제 | PR 머지 후 feature 브랜치 자동 삭제 |
| Linked Issue | PR은 관련 이슈 연결 필수 (`Closes #123`) |
