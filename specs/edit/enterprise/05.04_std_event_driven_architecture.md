# Enterprise Spec — 이벤트 드리븐 아키텍처 (EDA / Messaging)

> 조직 전체 서비스가 이벤트를 통해 **결합도 최소화·비동기 처리·장애 격리**를 달성하기 위한 표준을 정의한다.  
> `08_data_platform_standards.md`의 데이터 파이프라인, `09_testing_strategy.md`의 계약 테스트와 연계한다.

## EDA 도입 기준

| 동기 방식의 문제 | EDA로 해결 |
|---------------|-----------|
| LLM 호출(~30s) 동안 HTTP 연결 유지 | 비동기 처리 후 결과 폴링/WebSocket 전달 |
| 외부 API 장애 시 요청 유실 | 큐에 적재 → 장애 복구 후 재처리 |
| 서비스 간 강결합 | 이벤트 발행/구독으로 결합 제거 |
| 순간 트래픽 급증 | 큐가 버퍼 역할 → 백엔드 보호 |
| 데이터 변경 전파 | Change Data Capture(CDC) 이벤트 |

### 언제 동기(REST/gRPC)를 쓰는가

```
동기 REST/gRPC                EDA (Kafka)
─────────────────             ──────────────────────────
즉시 응답 필요                처리 시간 불확실 (LLM, 외부 API)
강한 일관성 요구              최종 일관성(Eventual Consistency) 허용
단순 CRUD                    복잡한 워크플로우·오케스트레이션
사용자 인터랙션 응답          배치·대용량 이벤트 스트리밍
```

## Enterprise Kafka 거버넌스

### 클러스터 구성

| 클러스터 | 용도 | 환경 |
|---------|------|------|
| `kafka-platform` | 플랫폼 이벤트 (캐시 무효화, 배포 알림) | prod/staging |
| `kafka-data` | 데이터 파이프라인 (CDC, 배치 이벤트) | prod/staging |
| `kafka-app` | 서비스 간 비즈니스 이벤트 | prod/staging |
| `kafka-dev` | 개발·테스트 통합 클러스터 | dev |

### 토픽 네이밍 규칙

```
{domain}.{subdomain}.{event-type}[.{version}]

예시:
  market-data.sp500.price-updated.v1      # S&P 500 가격 업데이트
  market-data.pipeline.dag-completed.v1   # DAG 완료 이벤트
  platform.cache.invalidate.v1            # 캐시 무효화 명령
  auth.user.login-succeeded.v1            # 사용자 로그인
  billing.invoice.payment-failed.v1       # 결제 실패

규칙:
  - 소문자·하이픈 구분 (도메인, 서브도메인, 이벤트타입)
  - 이벤트명은 과거형 동사 (completed, failed, updated) — 일어난 사실
  - 명령은 현재형 (invalidate) — 수행할 행동
  - 버전 필수 (v1, v2) — Breaking Change 시 신규 버전 토픽
```

### 파티션 키 전략

| 기준 | 파티션 키 | 효과 |
|------|---------|------|
| 사용자별 순서 보장 | `user_id` | 동일 사용자 이벤트 순서 유지 |
| 도메인별 집약 | `ticker` / `sector_id` | 동일 데이터 함께 처리 |
| 최대 병렬화 | 없음 (round-robin) | 처리량 최대화 |
| 테넌트 분리 | `tenant_id` | 멀티테넌트 격리 |

### 토픽 보존·파티션 기준

| 토픽 유형 | 보존 기간 | 파티션 수 | 근거 |
|----------|---------|--------|------|
| 비즈니스 이벤트 | 7일 | 서비스 수 × 3 | 재처리 여유 |
| 감사 로그 | 1년 | 12 | 법적 요건 |
| 데이터 파이프라인 | 3일 | 처리 병렬도 기준 | |
| 플랫폼 운영 | 24시간 | 6 | 단기 운영성 |

## Schema Registry (Avro / Protobuf)

이벤트 스키마는 **Schema Registry**에 등록해 Producer·Consumer 간 호환성을 자동 검증한다.

### 스키마 등록 원칙

```
모든 Kafka 이벤트 → Schema Registry 등록 필수
  ├─ Avro (기본): 스키마 진화 강력, 직렬화 효율
  └─ Protobuf (gRPC 연동 시): 타입 안전
```

```python
# Avro 스키마 예시 — market-data.sp500.price-updated.v1
PRICE_UPDATED_SCHEMA = {
    "type": "record",
    "name": "SpStockPriceUpdated",
    "namespace": "com.corp.market_data.v1",
    "fields": [
        {"name": "event_id",      "type": "string"},
        {"name": "event_type",    "type": "string", "default": "price-updated"},
        {"name": "version",       "type": "string", "default": "1.0"},
        {"name": "timestamp",     "type": "long", "logicalType": "timestamp-millis"},
        {"name": "source",        "type": "string"},
        {"name": "correlation_id","type": ["null", "string"], "default": None},
        {"name": "payload", "type": {
            "type": "record",
            "name": "PricePayload",
            "fields": [
                {"name": "ticker",      "type": "string"},
                {"name": "trade_date",  "type": "string"},
                {"name": "close_price", "type": "double"},
                {"name": "volume",      "type": "long"}
            ]
        }}
    ]
}
```

### 스키마 호환성 정책

| 정책 | 허용 변경 | 금지 변경 |
|------|---------|---------|
| BACKWARD (기본) | 선택 필드 추가 | 필수 필드 추가, 필드 삭제 |
| FORWARD | 필드 삭제 | 필수 필드 추가 |
| FULL | 선택 필드 추가만 | 그 외 모두 |

> **Breaking Change** 시: 신규 버전 토픽 생성 → 소비자 마이그레이션 기간 제공 → 구버전 Deprecation

## 이벤트 설계 표준

### 공통 이벤트 Envelope

```python
from dataclasses import dataclass, field
from datetime import datetime, UTC
import uuid

@dataclass
class EventEnvelope:
    event_id: str = field(default_factory=lambda: str(uuid.uuid4()))
    event_type: str = ""              # 토픽명 (market-data.sp500.price-updated)
    version: str = "1.0"
    timestamp: str = field(
        default_factory=lambda: datetime.now(UTC).isoformat()
    )
    source: str = ""                  # 발행 서비스명
    correlation_id: str | None = None # 분산 트레이싱 연결
    payload: dict = field(default_factory=dict)
```

### 이벤트 타입 네이밍

```
{도메인}.{서브도메인}.{과거형-동사}  ← 일어난 사실 (이벤트)
{도메인}.{서브도메인}.{현재형-동사}  ← 수행할 명령 (커맨드)

✅ 좋은 예:
  market-data.pipeline.dag-completed
  auth.user.password-changed
  billing.invoice.payment-failed

❌ 나쁜 예:
  data_updated           (도메인 없음, 스네이크케이스)
  UserLoginEvent         (PascalCase, 접미사 Event)
  process                (모호한 동사원형)
```

## 분산 패턴 표준

### Saga 패턴 (분산 트랜잭션)

여러 서비스에 걸친 트랜잭션은 **Saga**로 관리한다. 2PC는 사용하지 않는다.

```
Choreography Saga (이벤트 체인)
  Service A → 이벤트 발행 → Service B 처리 → 이벤트 발행 → Service C
  실패 시: 각 서비스가 보상(Compensating) 이벤트 발행

Orchestration Saga (중앙 조율)
  Saga Orchestrator → Service A 호출 → Service B 호출 → ...
  실패 시: Orchestrator가 롤백 명령 순서 제어
  도구: Temporal, Conductor, 또는 LangGraph
```

### CQRS (Command Query Responsibility Segregation)

```
쓰기 모델 (Command Side)
  └─ 이벤트 발행 → Kafka
        │
        ▼
읽기 모델 (Query Side)
  └─ 이벤트 소비 → Materialized View 갱신
  └─ 조회 API → 읽기 최적화 모델 반환

예시:
  S&P 500 가격 수집(Command) → Kafka → Mart 집계(Query Side) → 대시보드 API
```

## DLQ (Dead Letter Queue) 표준

```
토픽: {원본토픽}.dlq

처리 실패 조건:
  ├─ 파싱 오류 (스키마 불일치)
  ├─ 비즈니스 규칙 위반
  └─ 재시도 횟수 초과 (기본 3회)

DLQ 모니터링:
  └─ DLQ 메시지 수 > 0 → Slack 즉시 알림
  └─ 24시간 이상 미처리 → PagerDuty

DLQ 재처리:
  └─ 원인 수정 후 수동 replay 또는 자동 재처리 잡
```

```python
# Consumer 표준 패턴 (재시도 + DLQ)
from tenacity import retry, stop_after_attempt, wait_exponential

@retry(
    stop=stop_after_attempt(3),
    wait=wait_exponential(min=1, max=30),
    reraise=True,
)
async def process_message(message: ConsumerRecord):
    try:
        event = parse_envelope(message.value)
        await handle_event(event)
    except Exception as e:
        if is_non_retryable(e):
            await send_to_dlq(message, reason=str(e))
            return
        raise  # 재시도
```

## 멱등성 표준

모든 Consumer는 **동일 이벤트를 2번 받아도 결과가 같아야** 한다.

```python
# 멱등성 보장 — event_id 기반 중복 처리 방지
async def handle_price_updated(event: EventEnvelope, db, redis):
    idempotency_key = f"processed:{event.event_id}"

    # 이미 처리된 이벤트면 skip
    if await redis.get(idempotency_key):
        log.info("duplicate_event_skipped", event_id=event.event_id)
        return

    # 비즈니스 로직 처리
    await upsert_price(db, event.payload)

    # 처리 완료 기록 (TTL: 이벤트 보존 기간 + 여유)
    await redis.setex(idempotency_key, 7 * 24 * 3600, "1")
```

## Consumer 설정 표준

```python
# Kafka Consumer 전사 표준 설정
CONSUMER_CONFIG = {
    "group_id": "{service}-{topic}-consumer",  # 서비스·토픽별 그룹 분리
    "auto_offset_reset": "earliest",           # 신규 그룹은 처음부터

    "session_timeout_ms": 45_000,
    "isolation_level": "read_committed",       # 트랜잭션 메시지만 소비
}
```

## 테스트 표준

```python
# 통합 테스트 — EmbeddedKafka 또는 Testcontainers
from testcontainers.kafka import KafkaContainer

@pytest.fixture(scope="session")
def kafka():
    with KafkaContainer("confluentinc/cp-kafka:7.6") as k:
        yield k

def test_price_updated_event_processed(kafka, db):
    producer = KafkaProducer(bootstrap_servers=kafka.get_bootstrap_server())
    consumer_service = PriceConsumerService(bootstrap_servers=...)

    event = EventEnvelope(
        event_type="market-data.sp500.price-updated.v1",
        source="ingest-pipeline",
        payload={"ticker": "AAPL", "trade_date": "2026-05-01", "close_price": 186.9},
    )
    producer.send("market-data.sp500.price-updated.v1", value=event.to_avro())
```
