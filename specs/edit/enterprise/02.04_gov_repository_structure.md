# Enterprise Spec — Git 레포지토리 구조 표준 (Repository Structure)

> 여러 애플리케이션을 Git으로 통합 관리할 때의 **레포 분리 기준·내부 구조·의존 관계**를 정의한다.  
> `02.02_gov_branch_strategy.md`, `04.01_std_platform_engineering.md`, `04.03_std_gitops.md`와 연계한다.

---

## 전체 레포 맵 (GitHub Organization)

```
github.com/corp/
│
├── 📦 [플랫폼·공유 레포]
│   ├── platform-sdk/          ← @corp/sdk-python, @corp/sdk-java (공용 라이브러리)
│   ├── design-system/         ← @corp/design-system (NPM 패키지)
│   ├── infra/                 ← GitOps 중앙 (ArgoCD, Kyverno, Helm Chart)
│   ├── data-platform/         ← 전사 Airflow DAG, dbt 모델, Data Contract
│   └── backstage-catalog/     ← Backstage Software Catalog 항목
│
├── 📋 [스펙 레포]
│   └── specs/                 ← enterprise/ + 서비스별 specs/ 연결 허브
│
└── 🚀 [서비스 레포] (멀티레포)
    ├── sp500-platform/        ← 예시 서비스 1
    ├── admin-portal/          ← 예시 서비스 2
    └── auth-service/          ← 예시 서비스 3
```

---

## 레포 유형별 역할

| 레포 | 유형 | 소유팀 | 배포 주기 |
|------|------|--------|---------|
| `infra` | GOV | Platform Engineering | ArgoCD Push (GitOps) |
| `platform-sdk` | LIB | Platform Engineering | SemVer 릴리스 |
| `design-system` | LIB | Design System 팀 | SemVer 릴리스 |
| `data-platform` | DATA | Data Platform 팀 | Airflow 스케줄 |
| `specs` | SPEC | ARB / 전체 팀 | PR 리뷰 |
| `{service}` | APP | 각 제품 팀 | 매 커밋 → CD |

---

## 레포 분리 기준

```
단일 레포로 유지               분리 조건 (→ 별도 레포)
─────────────────              ──────────────────────────
같은 팀이 소유                 2개 이상 팀이 독립 배포 필요
같은 릴리스 주기               서로 다른 릴리스 사이클
동일 기술 스택                 다른 언어·프레임워크 필요
단순 의존 관계                 순환 의존 발생 위험
```

## 레포 간 의존성 다이어그램

```
[specs]
    │ 스펙 정의
    ▼
[{service}]  ──────────────────────────────────────────────────────┐
    │ Dockerfile 빌드                  │ DAG 코드                   │
    │ image push (git-sha)             │                            │
    ▼                                 ▼                            │
[infra]                    [data-platform]              의존(import)│
    │ ArgoCD Sync                      │                            │
    ▼                                 ▼                            │
[K8s Cluster]              [Airflow Cluster]            ◄──────────┘
                                                     platform-sdk
                                                     design-system
```

**단방향 의존 원칙:**
```
{service} → platform-sdk    ✅ (서비스가 SDK를 소비)
platform-sdk → {service}    ❌ (금지 — 순환 의존)
{service} → design-system   ✅ (프론트엔드만)
{service} → {service}       ❌ (직접 import 금지 → API 또는 이벤트로만)
```

## Golden Path 레포 생성 (Backstage Template)

Backstage가 `{service}` 구조를 자동 생성한다 (`04.01_std_platform_engineering.md`).

```bash
# 개발자가 Backstage에서 클릭 한 번으로 생성되는 것:
gh repo create corp/{service-name} --template corp/golden-path-template

# 자동 포함 항목:
# - specs/ 디렉토리 (비즈니스 스펙 템플릿)
# - apps/api/ (FastAPI 또는 Spring Boot 선택)
# - apps/frontend/ (React + Vite + pnpm)
# - .github/workflows/ (CI·prototype·release)
# - CODEOWNERS
# - catalog-info.yaml (Backstage 자동 등록)
# - Helm Chart (infra 레포에 자동 PR)
# - ArgoCD Application (infra/apps/dev/ 자동 추가)
```

## 브랜치 전략 적용 (`02.02_gov_branch_strategy.md`)

| 레포 유형 | 브랜치 모델 | 이유 |
|----------|-----------|------|
| `{service}` | GitHub Flow (main + feature/*) | 자주 배포, 단순 |
| `platform-sdk` | GitHub Flow + SemVer Tag | 라이브러리 릴리스 필요 |
| `design-system` | GitHub Flow + Turborepo | 모노레포, 선택적 배포 |
| `infra` | GitOps (main이 프로덕션) | 선언적 배포 |
| `data-platform` | GitHub Flow | DAG는 Airflow가 실행 |
| `specs` | GitHub Flow + ARB 리뷰 | 변경 시 승인 필요 |

## 시크릿·설정 관리 (`04.02_gov_zero_trust_security.md`)

```
레포에 절대 저장 금지:
  - API 키, 패스워드, 토큰
  - 환경별 접속 정보

저장 위치:
  - K8s Secret (Sealed Secrets 암호화) → infra/ 레포
  - Vault Dynamic Secret → 런타임 주입
  - GitHub Secrets → CI/CD 용도만
  - .env.example → 필요한 환경변수 목록만 (값 없이)
```
