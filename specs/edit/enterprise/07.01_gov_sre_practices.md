# Enterprise Spec — SRE Practices (SLO/SLI/Error Budget)

> **신뢰성을 수치로 정의하고 오류 예산으로 혁신과 안정의 균형**을 맞추는 SRE 조직 표준을 정의한다.

---

## 핵심 개념

| 용어 | 정의 | 예시 |
|------|------|------|
| SLI (Service Level Indicator) | 신뢰성을 측정하는 지표 | 요청 성공률, p99 응답시간 |
| SLO (Service Level Objective) | SLI의 목표값 | 성공률 ≥ 99.9% (30일 기준) |
| Error Budget | SLO를 유지하면서 허용되는 오류 여유 | 99.9% SLO → 월 43.8분 다운타임 허용 |
| SLA (Service Level Agreement) | 고객과의 계약상 목표 (SLO보다 낮게 설정) | 가용성 99.5% 보장 |
| Toil | 수동·반복·자동화 가능한 운영 작업 | 매뉴얼 배포, 수동 알림 확인 |

## SLO 정의 표준

### SLO 문서 구조

```yaml
# slo/sp500-api.yaml
service: sp500-api
owner: data-platform-team
version: "1.0"
review_cycle: quarterly

slis:
  - name: availability
    description: "전체 요청 중 성공(2xx/3xx) 비율"
    query: |
      sum(rate(http_requests_total{service="sp500-api", code=~"2..|3.."}[5m]))
      /
      sum(rate(http_requests_total{service="sp500-api"}[5m]))
    good_threshold: 0.999

  - name: latency
    description: "API 응답시간 p95 기준"
    query: |
      histogram_quantile(0.95,
        rate(http_request_duration_seconds_bucket{service="sp500-api"}[5m])
      )
    good_threshold: 2.0   # 2초 이내

  - name: pipeline_completion
    description: "거래일 기준 파이프라인 완료율"
    query: |
      count(pipeline_completed_total{dag="run_agent_trend", status="success"})
      /
      count(trading_days_total)
    good_threshold: 0.95

slos:
  - sli: availability
    target: 99.9%
    window: 30d
    error_budget_policy: slow-burn   # 빠른 소진 방지

  - sli: latency
    target: 95%
    window: 30d

  - sli: pipeline_completion
    target: 95%
    window: 30d

alerting:
  burn_rate_fast:   # 1시간 내 Error Budget 2% 소진 시
    severity: page
    window: 1h
    burn_rate: 14.4
  burn_rate_slow:   # 6시간 내 Error Budget 5% 소진 시
    severity: ticket
    window: 6h
    burn_rate: 6
```

### Error Budget 계산

| SLO | 기간 | 허용 다운타임 | 허용 오류 비율 |
|-----|------|------------|-------------|
| 99.9% | 30일 | 43.8분 | 0.1% |
| 99.5% | 30일 | 3.6시간 | 0.5% |
| 99.0% | 30일 | 7.2시간 | 1.0% |
| 95.0% | 30일 | 36시간 | 5.0% |

## Error Budget Policy

### Error Budget 소진 시 대응 단계

| 소진율 | 대응 |
|--------|------|
| 0~50% | 정상 개발·배포 허용 |
| 50~75% | 기능 개발 속도 조절, 안정성 작업 비중 확대 |
| 75~100% | 기능 배포 동결, 신뢰성 개선에만 집중 |
| 100% 초과 | 긴급 Freeze — 프로덕션 변경 금지, SRE 승인 필요 |

```
[Error Budget 소진 알림 흐름]
  Prometheus AlertManager
    → Burn Rate 빠름 (14.4x): PagerDuty 호출
    → Burn Rate 느림 (6x): Slack + Jira 티켓 자동 생성
    → 50% 소진: 주간 리뷰 의제에 자동 추가
    → 75% 소진: Engineering Manager 에스컬레이션
```

## Toil 관리

### Toil 정의 기준

모든 **수동·반복·자동화 가능** 작업은 Toil로 분류한다.

| Toil 유형 | 예시 | 자동화 방법 |
|----------|------|-----------|
| 수동 배포 | 매뉴얼 kubectl apply | GitOps(ArgoCD) |
| 수동 스케일링 | 피크 전 Pod 수 조정 | HPA + KEDA |
| 반복 알림 확인 | "이거 장애인지 확인해줘" Slack | 알림 품질 개선 + Runbook |
| DB 정리 작업 | 만료 데이터 수동 삭제 | 배치 DAG 자동화 |
| 인증서 갱신 | 수동 TLS 인증서 교체 | cert-manager 자동 갱신 |

### Toil 측정 및 목표

```
팀별 업무 시간 중 Toil 비율
  현재: 측정 후 기록
  목표: 50% 미만
  우수: 25% 미만

분기별 Toil 감소 목표: 10% 이상
```

## Incident Management

### Severity 정의

| Severity | 기준 | 대응 시작 | 커뮤니케이션 |
|----------|------|---------|------------|
| SEV-1 | 전체 서비스 중단 또는 데이터 손실 | 5분 이내 | 즉시 경영진 보고 |
| SEV-2 | 핵심 기능 장애, 50% 이상 사용자 영향 | 15분 이내 | 1시간 내 상태 업데이트 |
| SEV-3 | 부분 기능 저하, 25% 미만 영향 | 1시간 이내 | 4시간 내 상태 업데이트 |
| SEV-4 | 경미한 이슈, 사용자 영향 없음 | 업무 시간 내 | — |

### Incident 흐름

```
1. 감지: PagerDuty 알림 또는 사용자 제보
        │
2. 대응: On-call 엔지니어 ACK (5분 이내, SEV-1)
        │
3. 트리아지: 영향 범위·심각도 결정, War Room 개설 (Slack Channel #incident-YYYYMMDD-N)
        │
4. 완화: 즉각적 조치 (트래픽 차단, 롤백, 스케일 아웃)
        │
5. 해결: 근본 원인 해결 또는 우회책 확보
        │
6. 복구 선언: 모든 SLI 정상 확인
        │
7. 사후 검토 (Postmortem): 5 업무일 이내 작성·공유
```

## Chaos Engineering

**목표**: 장애를 미리 주입해 시스템의 약점을 사전 발견한다.

### 도입 단계

| 단계 | 내용 | 도구 |
|------|------|------|
| 1. 가설 수립 | "Redis 장애 시 API가 Cache-Aside로 정상 동작한다" | — |
| 2. 통제된 실험 | dev 환경에서 Redis 컨테이너 kill | Chaos Mesh |
| 3. 결과 관찰 | API 응답 정상 여부, Error Budget 영향 | Grafana |
| 4. 자동화 | 주간 자동 카오스 실험 스케줄 | Chaos Mesh CronJob |

```yaml
# Chaos Mesh — Redis 장애 주입
apiVersion: chaos-mesh.org/v1alpha1
kind: PodChaos
metadata:
  name: redis-failure-test
spec:
  action: pod-kill
  mode: one
  selector:
    namespaces: [dev]
    labelSelectors:
      app: redis
  scheduler:
    cron: "0 10 * * 1"   # 매주 월요일 10:00 UTC
```

## Living Spec 연계 (Level 4+) — SLO → 스펙 갱신 트리거

SLO 미달이 발생하면 **스펙 재검토를 자동으로 트리거**한다 (`07.02_std_living_specification.md` 참조).

```
Error Budget 빠른 소진 감지 (AlertManager)
    │  webhook
    ▼
Jira 이슈 자동 생성 (label: spec-review-required)
  - 어떤 SLO가 미달인가
  - 비기능 요건 재검토 체크리스트
  - 관련 스펙 파일 링크
    │  PO + Tech Lead 검토
    ▼
스펙 수정 PR → AI Validator 검증 (09.01 참조)
```

```yaml
# AlertManager 설정 — SLO 미달 시 스펙 리뷰 webhook
receivers:
  - name: spec-review-trigger
    webhook_configs:
      - url: "https://spec-sync.internal/webhook/slo-alert"
```
