# Enterprise Spec — Zero Trust 보안 & 공급망 보안

> 조직 전체 **Zero Trust 보안 아키텍처와 공급망 보안** 표준을 정의한다.  
> 핵심: "신뢰는 증명된다(Trust is verified), 가정되지 않는다(never assumed)"

---

## Zero Trust 아키텍처

### 원칙

| 원칙 | 구현 방법 |
|------|----------|
| 명시적 검증 | 모든 요청에 Identity + Device + Context 검증 |
| 최소 권한 | 작업별 최소 권한, 시간 제한 토큰 |
| 침해 가정 | 내부망도 외부망과 동일하게 취급 (mTLS, 암호화) |
| 지속 검증 | 세션 중에도 지속적 신뢰 재검증 |

### 아키텍처

```
[외부 클라이언트]
        │ TLS 1.3
        ▼
[Zero Trust Edge (API Gateway + WAF)]
  ├─ DDoS 보호
  ├─ Bot 탐지
  ├─ Geo-IP 필터링
  └─ JWT/OIDC 검증
        │ mTLS (SPIFFE/SPIRE)
        ▼
[Service Mesh (Istio)]
  ├─ 서비스 간 mTLS (자동 인증서 회전)
  ├─ 트래픽 정책 (AuthorizationPolicy)
  └─ Workload Identity (SPIFFE SVID)
        │
        ▼
[백엔드 서비스]
        │ 동적 시크릿 (Vault)
        ▼
[데이터 스토어]
```

## Workload Identity (SPIFFE/SPIRE)

서비스가 "어떤 사람"이 아닌 "어떤 워크로드"인지 증명한다.

```yaml
# SPIFFE SVID 예시
# 서비스 ID: spiffe://corp.example.com/ns/finance/sa/sp500-api
# 인증서 유효시간: 1시간 (자동 갱신)
# 서비스 간 통신: mTLS로 자동 암호화

# Istio AuthorizationPolicy — 서비스 간 접근 제어
apiVersion: security.istio.io/v1beta1
kind: AuthorizationPolicy
metadata:
  name: sp500-api-policy
  namespace: finance
spec:
  selector:
    matchLabels:
      app: sp500-api
  rules:
    - from:
        - source:
            principals:
              - "cluster.local/ns/finance/sa/frontend"   # 허용된 호출자만
      to:
        - operation:
            methods: ["GET"]
            paths: ["/api/v1/*"]
```

## Secrets 관리 (HashiCorp Vault)

### 동적 시크릿 (Dynamic Secrets)

```
[앱 서버 시작]
  1. Vault에 AppRole 또는 K8s SA 토큰으로 인증
  2. Vault → 앱 전용 DB 사용자 생성 (유효 TTL: 1시간)
  3. 앱 → DB 접속 (앱 전용 자격증명)
  4. TTL 만료 전 자동 갱신 (Vault Agent)
  5. 앱 종료 → DB 사용자 자동 삭제
```

```hcl
# Vault 정책 — sp500-api 서비스 전용
path "database/creds/sp500-api-role" {
  capabilities = ["read"]
}
path "secret/data/sp500-api/*" {
  capabilities = ["read"]
}
```

### 시크릿 분류 및 처리 기준

| 유형 | 저장 위치 | TTL | 로테이션 |
|------|----------|-----|---------|
| DB 자격증명 | Vault (동적) | 1시간 | 자동 |
| API 키 (외부) | Vault (정적) | 90일 | 반자동 |
| JWT 서명키 | Vault (PKI) | 1년 | 자동 |
| 환경별 설정 | Sealed Secrets (K8s) | — | PR |
| LLM API 키 | Vault + LLM Gateway | 90일 | 반자동 |

## 공급망 보안 (Supply Chain Security)

### SLSA (Supply Chain Levels for Software Artifacts)

| 레벨 | 요건 | 현재 목표 |
|------|------|----------|
| SLSA L1 | 빌드 스크립트 존재, Provenance 생성 | ✅ 즉시 적용 |
| SLSA L2 | 버전 관리, 호스팅 빌드 서비스 | ✅ 즉시 적용 |
| SLSA L3 | 분리된 빌드 환경, 비위변조 Provenance | 6개월 내 목표 |
| SLSA L4 | 이중 검토, Hermetic 빌드 | 장기 목표 |

### Sigstore (이미지 서명)

```bash
# CI에서 이미지 빌드 후 서명
docker build -t ghcr.io/org/sp500-api:${GIT_SHA} .
docker push ghcr.io/org/sp500-api:${GIT_SHA}

# Cosign으로 키리스(keyless) 서명 — OIDC 기반
cosign sign --yes ghcr.io/org/sp500-api:${GIT_SHA}

# 배포 전 서명 검증 (Kyverno Policy에서 자동 수행)
cosign verify ghcr.io/org/sp500-api:${GIT_SHA} \
  --certificate-identity-regexp="https://github.com/org/.*" \
  --certificate-oidc-issuer="https://token.actions.githubusercontent.com"
```

### SBOM (Software Bill of Materials)

```bash
# Syft로 SBOM 생성 (SPDX 또는 CycloneDX 형식)
syft ghcr.io/org/sp500-api:${GIT_SHA} -o spdx-json > sbom.spdx.json

# Grype로 SBOM 기반 취약점 스캔
grype sbom:./sbom.spdx.json --fail-on high

# SBOM을 Rekor (Sigstore Transparency Log)에 기록
cosign attest --predicate sbom.spdx.json \
  --type spdxjson ghcr.io/org/sp500-api:${GIT_SHA}
```

### GitHub Actions CI 보안 게이트

```yaml
# .github/workflows/security.yml
jobs:
  security:
    steps:
      - name: SAST (Semgrep)
        uses: semgrep/semgrep-action@v1
        with:
          config: "p/owasp-top-ten p/python"

      - name: SCA (의존성 취약점)
        run: |
          pip install pip-audit
          pip-audit --requirement requirements.txt --fail-on-vuln-sev HIGH

      - name: Container Scan (Trivy)
        uses: aquasecurity/trivy-action@v0.18.0
        with:
          image-ref: ghcr.io/org/${{ env.SERVICE }}:${{ github.sha }}
          severity: CRITICAL,HIGH
          exit-code: 1

      - name: SBOM 생성 및 서명
        run: |
          syft $IMAGE -o cyclonedx-json > sbom.json
          cosign attest --predicate sbom.json --type cyclonedx $IMAGE
```

## Compliance as Code (OPA/Kyverno)

정책을 코드로 작성해 K8s 클러스터에서 자동 강제한다.

### Kyverno 정책 예시

```yaml
# 정책 1: root 컨테이너 금지
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: disallow-root-user
spec:
  validationFailureAction: Enforce
  rules:
    - name: check-runAsNonRoot
      match:
        resources: { kinds: [Pod] }
      validate:
        message: "컨테이너는 root(0)로 실행할 수 없습니다."
        pattern:
          spec:
            containers:
              - securityContext:
                  runAsNonRoot: true

# 정책 2: 서명된 이미지만 허용
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: require-signed-image
spec:
  validationFailureAction: Enforce
  rules:
    - name: verify-image-signature
      match:
        resources: { kinds: [Pod] }
      verifyImages:
        - image: "ghcr.io/org/*"
          attestors:
            - entries:
                - keyless:
                    subject: "https://github.com/org/*"
                    issuer: "https://token.actions.githubusercontent.com"

# 정책 3: 리소스 제한 필수
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: require-resource-limits
spec:
  validationFailureAction: Enforce
  rules:
    - name: check-limits
      match:
        resources: { kinds: [Pod] }
      validate:
        message: "CPU/Memory limits 설정이 필요합니다."
        pattern:
          spec:
            containers:
              - resources:
                  limits:
                    cpu: "?*"
                    memory: "?*"
```

## Enterprise SSO / Identity Federation

### 엔터프라이즈 IdP 통합

조직 내 모든 인증은 **Keycloak을 중앙 IdP**로 사용하고, 외부 사용자 저장소와 연동한다.

```
[사용자]
  └─ Keycloak (Enterprise Realm)
        ├─ 내부 직원 → LDAP / Active Directory (User Federation)
        ├─ 파트너 → SAML 2.0 / OIDC Federation
        └─ 시스템 계정 → Client Credentials (M2M)
```

### LDAP / Active Directory 연동

```yaml
# Keycloak User Federation — LDAP 설정
federation:
  vendor: ACTIVE_DIRECTORY
  connectionUrl: "ldaps://ad.corp.example.com:636"
  bindDn: "cn=keycloak-svc,ou=service-accounts,dc=corp,dc=example,dc=com"
  bindCredential: "${LDAP_BIND_PASSWORD}"   # Vault 주입
  usersDn: "ou=employees,dc=corp,dc=example,dc=com"
  syncMode: FORCE                            # 로그인마다 동기화
  useTruststoreSpi: ALWAYS                   # TLS 검증
  periodicFullSync: true
  fullSyncPeriod: 3600                       # 1시간마다 전체 동기화
```

### SCIM 사용자 프로비저닝

HR 시스템 → SCIM → Keycloak 사용자 자동 생성·삭제

```
입사: HR 시스템 → SCIM POST /Users → Keycloak 계정 생성 → 기본 역할 할당
퇴사: HR 시스템 → SCIM PATCH /Users (active=false) → 계정 즉시 비활성화
```

### Multi-Realm 운영 기준

| Realm | 용도 | 사용자 |
|-------|------|--------|
| `corp-internal` | 내부 직원용 모든 서비스 | LDAP/AD 연동 |
| `corp-partner` | 파트너사 접근 | 외부 IdP Federation |
| `corp-dev` | 개발·테스트 환경 | 개발자 계정 |

**원칙**: Realm 간 사용자 공유 금지. 서비스는 해당 Realm에만 등록한다.

### 역할 매핑 표준

```yaml
# LDAP 그룹 → Keycloak 역할 매핑
groupMapper:
  - ldapGroup: "CN=Data-Analysts,OU=Groups,DC=corp"
    keycloakRole: "analyst"
  - ldapGroup: "CN=Data-Engineers,OU=Groups,DC=corp"
    keycloakRole: "data-engineer"
  - ldapGroup: "CN=SRE-Team,OU=Groups,DC=corp"
    keycloakRole: "sre"
```
