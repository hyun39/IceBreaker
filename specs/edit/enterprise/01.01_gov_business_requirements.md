# Enterprise Spec — 비즈니스 요건 정의·분석 표준

> 이 문서는 **"무엇을 만들지 결정하는 방법"** — 요구 발견·검증·우선순위화·추적까지 조직 표준을 정의한다.  
> 비즈니스 스펙 작성 양식은 이 문서 하단 **§ 비즈니스 스펙 작성 템플릿** 섹션을 사용한다.  
> 모든 기술 스펙(02~16)은 이 단계를 통과한 요건에서 시작된다.

---

## 전체 흐름

```
[1. 문제 발견]
  고객 인터뷰, 데이터 분석, 지원 티켓 패턴
        │
        ▼
[2. 기회 정의]
  OKR 연계, 임팩트 매핑, 기회 가설 작성
        │
        ▼
[3. 요건 초안 구조화]
  유저 스토리 초안, 핵심 화면 흐름 정의
        │
        ▼
[4. 프로토타입 우선 검증] ◀ ── ── ── ┐
  Lo-fi Sketch → Hi-fi Figma → Coded Mockup  │
  사용자 테스트·이해관계자 데모              │
        │                                    │
        ├─ 가설 불일치 → 재설계 ─────────────┘
        │
        ▼
[5. 요건 확정·우선순위 결정]
  검증된 요건 → RICE / MoSCoW / DoR 체크
        │
        ▼
[6. 스펙 문서 작성]
  이 문서 하단 § 비즈니스 스펙 작성 템플릿 사용
        │
        ▼
[7. 본격 개발 → 가설 검증]
  MVP 출시 → 지표 측정 → Build-Measure-Learn
        │
        ▼
[8. 추적·회고]
  요건 추적 매트릭스, 비즈니스 KPI 달성 여부
```

> **핵심 원칙**: 코드 한 줄 작성 전에 프로토타입으로 먼저 검증한다.  
> 프로토타입은 "버리는 것"이 아니라 **요건을 시각화·검증하는 도구**이며, 검증된 패턴은 프로덕션 코드의 기반이 된다.

## 1. 문제 발견 (Problem Discovery)

### 인풋 소스

| 소스 | 방법 | 담당 |
|------|------|------|
| 사용자 인터뷰 | 월 2회 이상, 구조화된 질문 | PO + UX |
| 데이터 분석 | 이탈률, 오류율, 사용 패턴 | Analytics |
| 지원 티켓 | Top 10 반복 이슈 주간 분석 | CS + PO |
| 이해관계자 요청 | 분기별 로드맵 미팅 | PO |
| 경쟁 분석 | 분기별 | 전략팀 |

### 문제 정의 문장 (Problem Statement)

```
[현재 상태]: ______는 ______하려고 할 때
[불편함]: ______라는 문제를 경험한다.
[영향]: 이 때문에 ______의 결과가 발생한다.
[목표]: 이를 해결하면 ______의 가치를 제공할 수 있다.

예시:
  투자 분석 담당자는 매 거래일 Sector 트렌드를 파악하려고 할 때,
  수작업으로 여러 소스를 취합해야 하는 문제를 경험한다.
  이 때문에 하루 30분 이상의 반복 작업이 발생하고 분석 일관성이 떨어진다.
  이를 해결하면 분석 준비 시간을 없애고 의사결정 품질을 높일 수 있다.
```

## 2. OKR 연계 (OKR Alignment)

### 모든 요건은 OKR에 연결해야 한다

요건이 OKR에 연결되지 않으면 **우선순위 경쟁에서 탈락**한다.

```
회사 OKR
  └─ Objective: 데이터 기반 의사결정 문화 정착
       └─ KR 1: 분석 도구 일일 활성 사용자(DAU) 100명 이상 (2026 Q2)
       └─ KR 2: 수작업 분석 보고서 90% 자동화 (2026 Q3)

팀 OKR (Data Platform)
  └─ Objective: 분석가 생산성 2배 향상
       └─ KR 1: S&P 500 분석 소요 시간 30분 → 0분
       └─ KR 2: LLM 트렌드 분석 정확도 85% 이상

요건 (sp500-trend-agent)
  └─ 기여하는 KR: "수작업 분석 보고서 90% 자동화"
  └─ 측정 지표: Trend Analysis 완료율, 사용자 체류 시간
```

**OKR 연계 없는 요건 처리**:

| 상황 | 처리 |
|------|------|
| 현재 OKR에 없음 | Backlog 유지, 다음 분기 OKR 검토 |
| 어떤 KR에도 기여 안 함 | PO가 신규 KR 제안하거나 Drop |
| 기술 부채 해소 | SRE Error Budget 소진 시 우선 처리 |

## 3. 임팩트 매핑 (Impact Mapping)

**Why(목표) → Who(행위자) → How(행동 변화) → What(기능)**의 4단계로 요건의 근거를 추적한다.

```
WHY
  └─ DAU 100명 달성
      │
      WHO
      ├─ 퀀트 분석가
      │     │
      │     HOW
      │     ├─ 분석 준비 시간 단축
      │     └─ 분석 결과 신뢰 향상
      │           │
      │           WHAT
      │           ├─ ODS 원시 데이터 즉시 조회
      │           ├─ DW Sector 집계 자동화
      │           └─ LLM Trend Analysis 제공
      │
      WHO
      └─ 투자 전략 담당자
            HOW
            └─ 직관적 인사이트 소비
                  WHAT
                  └─ Trend 카드 UI (비기술자 친화적)
```

## 4. 프로토타입 우선 검증 (Prototype-First Validation)

> 요건을 글로만 작성하면 이해관계자마다 다르게 해석한다.  
> 프로토타입은 **"우리가 같은 것을 상상하고 있는가"를 값싸게 확인하는 도구**이다.  
> 본격 개발 전에 시각화·테스트해 방향 오류를 조기에 잡는다.

---

### 프로토타입 충실도 레벨 (Fidelity Levels)

| 레벨 | 도구 | 제작 시간 | 언제 사용하는가 | 검증 대상 |
|------|------|---------|--------------|---------|
| **L0** 종이·화이트보드 | 펜·포스트잇 | 30분 | 아이디어 초기 탐색, 팀 내 발산 | 핵심 흐름·개념 공유 |
| **L1** Lo-fi 와이어프레임 | Figma (Wireframe Kit) | 0.5~1일 | 화면 흐름·레이아웃 검증 | 정보 구조·네비게이션 |
| **L2** Hi-fi 목업 | Figma (디자인 완성) | 2~5일 | 시각 디자인·브랜드 검증, 이해관계자 데모 | 디자인 적합성·감성 |
| **L3** Coded Mockup | React + MSW (아래 상세) | 3~10일 | 인터랙션·실데이터 모양 검증, 복잡한 UI | UX 흐름·데이터 표현 |
| **L4** 프로덕션 MVP | 실 구현 | — | 실사용자 검증 | 비즈니스 가설 |

**선택 기준**:

```
불확실성 높음 → L0/L1부터 시작
  → 검증 완료 → L2/L3으로 정교화
    → 가설 확인 → L4 본격 개발

불확실성 낮음 (단순 기능 추가) → L1 또는 바로 DoR 체크 후 개발
```

---

### L1 — Lo-fi Figma 표준

**목적**: 화면 흐름과 정보 구조를 빠르게 팀과 맞춘다.

```
Figma 파일 구조 (팀 표준)
├── 📄 Cover          — 서비스명, 날짜, 담당자
├── 📄 User Flow      — 시나리오별 화면 흐름 화살표
├── 📄 Wireframes/
│   ├── 01_대시보드
│   ├── 02_ODS_탭
│   ├── 03_DW_탭
│   └── 04_Mart_탭
└── 📄 Notes          — 검증 결과, 피드백 정리
```

**피드백 수집 방법**:
- Figma 댓글 기능으로 이해관계자 비동기 리뷰
- 5명 사용자 인터뷰로 네비게이션·레이블 검증 (5명으로 80% 이슈 발견)

---

### L2 — Hi-fi Figma + Prototype 표준

**목적**: 실제 화면과 유사한 디자인으로 이해관계자 승인·사용성 테스트.

```
Figma Prototype 설정
  ├─ 클릭 인터랙션 (탭 이동, 모달 열기/닫기)
  ├─ 스크롤 동작 (테이블 가상 스크롤 시뮬레이션)
  └─ 상태별 화면 (로딩 중 / 데이터 없음 / 에러)
```

**Design Token 사용 원칙**: Hi-fi 단계부터 `@corp/design-system` 토큰(`color`, `spacing`, `typography`) 적용 → 프로덕션 이식 비용 최소화.

**승인 게이트**: Hi-fi 완성 후 **이해관계자 공식 승인** → `business_format.md` 스펙 작성 → DoR 진입.

---

### L0~L3 자동화 파이프라인 (AI-Assisted Prototype Generation)

> **목업은 최종 산출물이 아니라 요건을 진화시키는 도구다.**  
> AI가 비즈니스 스펙에서 L1·L2 목업을 자동 생성하고, 피드백이 요건을 정제하는 루프를 반복한다.  
> 상세 구현 및 요건 진화 사이클 전체는 **`02.02_std_prototype_driven_requirements.md`** 참조.

> **핵심 원칙**: React 코드 자체가 L1·L2·L3이다. Storybook이 시각적 리뷰 도구가 된다.

#### 자동화 가능 범위

| 단계 | 자동화율 | 사람이 해야 할 것 |
|------|---------|----------------|
| L0 → 화면 목록·흐름 추출 | ✅ 90% | 누락 화면 추가 |
| L0 → L1 Lo-fi 와이어프레임 | ✅ 80% | 레이아웃 조정, 정보 우선순위 |
| L1 → L2 Hi-fi 디자인 토큰 적용 | ✅ 70% | 브랜드·감성 판단 |
| L2 → L3 React 코드 | ✅ 75% | 인터랙션 세부 구현 |
| 사용자 테스트 | ❌ 0% | 반드시 실제 사람 |
| 이해관계자 승인 | ❌ 0% | 반드시 실제 사람 |

#### React-Native 자동화 파이프라인 (Figma 없이)

> **핵심 전환**: Figma/Uizard 외부 API 의존을 제거한다.  
> React 코드 자체가 L1·L2·L3이다 — **"코드가 곧 프로토타입"**.  
> Storybook이 Figma를 대체하는 시각적 검토 도구가 된다.

```
[비즈니스 스펙 PR 머지]
  (business_format.md — 유저스토리 + 인수기준)
        │
        ▼  GitHub Actions + LLM
[Step 1: 스펙 파싱]
  LLM이 유저스토리·시나리오·인수기준을
  화면 JSON으로 구조화 (screens, flows, states)
        │
        ▼  LLM 코드 생성 (gpt-4o-mini)
[Step 2: L1 React Skeleton 생성]
  회색 박스(div + bg-gray) 기반 레이아웃 TSX
  → 구조·계층·흐름만 표현, 스타일 없음
        │
        ▼  Python 스크립트 (컴포넌트 치환)
[Step 3: L2 React Hi-fi 업그레이드]
  회색 박스 → @corp/design-system 실제 컴포넌트 치환
  Skeleton·Alert·Tabs·DataTable·Badge 자동 매핑
  로딩/에러/빈 상태 자동 추가
        │
        ▼  Python 스크립트 (api_contract.md 파싱)
[Step 4: MSW 핸들러 자동 생성]
  api_contract.md TypeScript 인터페이스 → MSW handler
  픽스처 JSON 자동 생성 (실제 API 응답 모양)
        │
        ▼  Storybook 자동 빌드 → Chromatic 배포
[Step 5: 시각적 리뷰 환경]
  L1·L2 스토리 각각 → Chromatic PR Preview URL
  팀원이 브라우저에서 클릭·검토 가능
        │
        ▼
[PR 댓글 자동 게시]
  L1 Storybook URL · L2 Storybook URL
  로컬 실행 명령 · 검증 체크리스트
```

**Figma와의 비교**:

| 항목 | 기존 (Figma) | React-Native |
|------|------------|-------------|
| 외부 API | Figma + Uizard + v0.dev | 없음 (LLM만) |
| 코드→디자인 변환 | 필요 | 불필요 (코드=프로토타입) |
| 시각적 리뷰 | Figma | **Storybook + Chromatic** |
| 프로덕션 재사용 | 재작성 필요 | **그대로 이식** |
| 라이선스 비용 | Figma + Uizard | LLM API만 |

#### GitHub Actions 구현 (React-Native)

```yaml
# .github/workflows/prototype-generation.yml
name: React Prototype Generation

on:
  pull_request:
    paths: ["specs/**/*.business_spec.md"]
    types: [opened, synchronize]

jobs:
  generate-prototype:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v3
        with: { enable-cache: true }
      - uses: pnpm/action-setup@v4
        with: { version: 9 }
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: pnpm }

      # Step 1: 스펙 파일 찾기
      - name: Find Changed Spec File
        id: spec
        run: |
          SPEC=$(git diff --name-only ${{ github.event.before }} HEAD \
                  | grep "\.business_spec\.md$" | head -1)
          echo "spec_file=$SPEC" >> $GITHUB_OUTPUT

      # Step 2: LLM으로 스펙 파싱 → 화면 JSON
      - name: Parse Spec to Screens JSON
        id: parse
        run: |
          uv run python scripts/proto/parse_spec.py \
            --spec "${{ steps.spec.outputs.spec_file }}" \
            --output /tmp/screens.json
        env:
          OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}

      # Step 3: L1 React Skeleton 생성
      - name: Generate L1 React Skeleton
        run: |
          uv run python scripts/proto/gen_l1_skeleton.py \
            --screens /tmp/screens.json \
            --output apps/mockup/src/screens/l1/
        env:
          OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}

      # Step 4: L2 Design System 컴포넌트 치환
      - name: Upgrade to L2 Hi-fi
        run: |
          uv run python scripts/proto/gen_l2_hifi.py \
            --l1-dir apps/mockup/src/screens/l1/ \
            --design-system packages/design-system/component-map.json \
            --output apps/mockup/src/screens/l2/

      # Step 5: MSW 핸들러 자동 생성
      - name: Generate MSW Handlers
        run: |
          uv run python scripts/proto/gen_msw_handlers.py \
            --api-contract specs/api_contract.md \
            --output apps/mockup/src/mocks/handlers.ts

      # Step 6: Storybook 자동 생성 + 빌드
      - name: Generate Storybook Stories
        run: |
          uv run python scripts/proto/gen_stories.py \
            --screens /tmp/screens.json \
            --output apps/mockup/src/stories/

      - name: Build Mockup & Storybook
        run: |
          cd apps/mockup
          pnpm install --frozen-lockfile
          pnpm biome check --apply .       # 자동 포매팅
          pnpm tsc --noEmit                # 타입 검사
          pnpm build-storybook

      # Step 7: Chromatic 시각적 리뷰 배포
      - name: Deploy to Chromatic
        id: chromatic
        uses: chromaui/action@v1
        with:
          projectToken: ${{ secrets.CHROMATIC_PROJECT_TOKEN }}
          workingDir: apps/mockup
          onlyChanged: true

      # Step 8: PR 댓글 자동 게시
      - name: Post PR Comment
        uses: actions/github-script@v7
        with:
          script: |
            github.rest.issues.createComment({
              issue_number: context.issue.number,
              owner: context.repo.owner,
              repo: context.repo.repo,
              body: `## 🎨 React 프로토타입 자동 생성 완료

            | 레벨 | 링크 | 설명 |
            |------|------|------|
            | L1 Skeleton | [Storybook L1](${{ steps.chromatic.outputs.storybookUrl }}?path=/story/l1) | 레이아웃·구조 확인 |
            | L2 Hi-fi | [Storybook L2](${{ steps.chromatic.outputs.storybookUrl }}?path=/story/l2) | 실제 컴포넌트 적용 |
            | 인터랙티브 | [Chromatic Preview](${{ steps.chromatic.outputs.buildUrl }}) | 클릭 가능한 목업 |

            **로컬 실행**:
            \`\`\`bash
            cd apps/mockup && pnpm dev     # http://localhost:6006
            \`\`\`

            **다음 단계**:
            - [ ] L1 구조·흐름 팀 리뷰 (Chromatic 댓글)
            - [ ] L2 컴포넌트·상태 이해관계자 승인
            - [ ] 게릴라 테스트 3명 이상 진행
            - [ ] 재설계 불필요 → DoR 체크 → 개발 착수

            > ⚠️ AI 자동 생성 초안입니다. 반드시 사람이 검토 후 사용하세요.`
            });
```

#### Step 1 — 스펙 파싱 (`scripts/proto/parse_spec.py`)

```python
# scripts/proto/parse_spec.py
import json, sys
from openai import OpenAI

SYSTEM = """

스펙 내용:
{spec_content}

{{
  "feature_name": "기능명 (파일명용 snake_case)",
  "screens": [
    {{
      "id": "screen_ods",
      "name": "ODS 종목 조회",

      "user_roles": ["analyst", "viewer"],

        {{"type": "DatePicker", "label": "거래일 선택", "required": true}},
        {{"type": "Select",     "label": "Sector 필터", "required": false}},
        {{"type": "DataTable",  "label": "종목 가격 테이블", "columns": ["ticker","close","volume"]}},
        {{"type": "Pagination", "label": "페이지네이션"}}
      ],
      "states": ["loading", "success", "empty", "error"],
      "error_cases": ["비거래일", "데이터 없음"],
      "api_endpoints": ["/api/v1/ods/prices"]
    }}
  ],
  "flows": [
    {{"from": "screen_ods", "to": "screen_dw", "trigger": "DW 탭 클릭"}}
  ]

규칙:

- 예외 시나리오 → error_cases
- 빠진 상태(loading/empty/error)가 있으면 반드시 추가
"""

def main(spec_file: str, output: str):
    spec = open(spec_file).read()
    client = OpenAI()
    resp = client.chat.completions.create(
        model="gpt-4o-mini",
        temperature=0,
        response_format={"type": "json_object"},
        messages=[
            {"role": "system", "content": SYSTEM},
            {"role": "user", "content": PROMPT.format(spec_content=spec)},
        ],
    )
    data = json.loads(resp.choices[0].message.content)
    json.dump(data, open(output, "w"), ensure_ascii=False, indent=2)
```

```python
import {
  DatePicker, DataTable, BarChart, LineChart,
  Select, Badge, Card, Tabs, TabsList, TabsTrigger, TabsContent,

def upgrade_l1_to_l2(l1_file: Path, output_dir: Path):
```

### 사용자 검증 방법

#### 게릴라 테스트 (Guerrilla Testing)

빠르고 저비용으로 5명의 사용자로 핵심 문제를 발견한다.

```
진행 순서 (세션당 30~45분)
  1. 소개 (5분): "제품 테스트가 아닌 디자인 테스트입니다"
  2. 시나리오 제시 (1분): "오늘 IT Sector 트렌드를 확인하려 합니다"
  3. 발화 사고 (20분): "생각나는 것을 소리내어 말해주세요"
      - 관찰: 어디서 멈추는가? 어디서 실수하는가?
  4. 사후 인터뷰 (10분): "가장 불편한 부분은?" "기대와 달랐던 점은?"
  5. 메모 (5분): 관찰 패턴 즉시 기록
```

**5명으로 충분한 이유**: 첫 번째 사용자가 전체 이슈의 31%, 5명이면 85%를 발견한다 (Nielsen).

#### 이해관계자 데모 체크리스트

```
데모 전
  ├─ 검증할 질문 2~3개 사전 준비 ("이 화면 흐름이 직관적인가?")
  └─ 프로토타입 공유 링크 준비 (Figma Embed 또는 localhost URL)

데모 중
  ├─ 기능 설명 금지 → 스스로 탐색하게 유도
  └─ 반응·발화 메모

데모 후 피드백 분류
  ├─ 🔴 Must Fix: 핵심 흐름이 막히는 문제
  ├─ 🟡 Should Fix: 개선하면 좋은 UX 문제
  └─ 🟢 Nice to Have: 추후 고려 사항
```

## 5. 유저 스토리 & 인수 기준

### 유저 스토리 형식

```
As a [역할], I want to [행동], so that [가치/목적].

예시:
  As a 퀀트 분석가,
  I want to 당일 Sector별 RSI와 이동평균을 한 화면에서 확인하고 싶다,
  so that 개별 데이터 소스를 취합하는 수작업 없이 즉시 분석을 시작할 수 있다.
```

### 인수 기준 (Acceptance Criteria) — Gherkin 형식

```gherkin
# Feature: Mart Key Index 조회

Scenario: 거래일 Key Index 정상 조회
  Given 사용자가 analyst 역할로 로그인되어 있고
  And 2026-05-01은 미국 주식 거래일이며
  And 해당 날짜의 파이프라인이 완료된 상태이다
  When 사용자가 Mart Key Index 탭에서 날짜 2026-05-01을 선택하면
  Then 11개 Sector의 KPI 카드가 표시되어야 한다
  And 각 카드에는 RSI, MA5/MA20, advance_ratio가 포함되어야 한다
  And 로딩 완료는 1초 이내여야 한다

Scenario: 비거래일 선택 시 안내
  Given 사용자가 날짜 선택기에서 2026-05-03(일요일)을 선택하면
  When 시스템이 비거래일임을 감지하면
  Then "선택한 날짜는 비거래일입니다" 안내와 함께
  And 가장 최근 거래일(2026-05-01)의 데이터를 자동으로 표시해야 한다
```

## 6. 우선순위 결정 프레임워크

### RICE 스코어링

```
RICE = (Reach × Impact × Confidence) / Effort

Reach:      영향받는 사용자 수 / 분기 (예: 100명)
Impact:     0.25 / 0.5 / 1 / 2 / 3 (최소~대규모)
Confidence: 50% / 80% / 100% (추정 신뢰도)
Effort:     개발 인원월 (예: 2명 × 1개월 = 2)

예시:
  Feature A: (100 × 2 × 0.8) / 2 = RICE 80
  Feature B: (50 × 3 × 1.0) / 1 = RICE 150  ← 우선
```

### MoSCoW (출시 단위 판단)

| 레벨 | 기준 | 처리 |
|------|------|------|
| **Must Have** | 없으면 출시 불가, 핵심 가치 직결 | 이번 릴리스에 반드시 포함 |
| **Should Have** | 있어야 품질이 높아지나 없어도 동작 | 시간 허용 시 포함 |
| **Could Have** | 있으면 좋지만 우선순위 낮음 | 다음 릴리스 검토 |
| **Won't Have** | 이번 버전에서 명시적 제외 | Backlog 또는 Drop |

### Impact-Effort Matrix (긴급 판단)

```
        낮은 Effort          높은 Effort
         ┌───────────────────────────────┐
높은     │  Quick Win ✅     Major Project│
Impact   │  (즉시 착수)      (계획 필요)  │
         ├───────────────────────────────┤
낮은     │  Fill-in 📋      Avoid ❌     │
Impact   │  (시간 나면)      (하지 말 것) │
         └───────────────────────────────┘
```

## 7. 이해관계자 관리 (RACI)

### RACI 매트릭스

| 역할 | 정의 |
|------|------|
| **R** (Responsible) | 실제 작업을 수행하는 사람 |
| **A** (Accountable) | 최종 결정권·승인 책임자 (1명만 지정) |
| **C** (Consulted) | 의사결정 전 의견을 구해야 하는 사람 |
| **I** (Informed) | 결정 후 결과를 통보받는 사람 |

```
요건 정의 RACI 예시 (S&P 500 분석 서비스)

                    PO   개발팀  분석팀  보안팀  경영진
문제 정의             A     C      C       I       I
요건 우선순위 결정     A     C      C       I       C
UI/UX 설계           C     C      A       I       I
기술 아키텍처 결정     C     A      I       C       I
보안 요건 승인        C     C      C       A       I
출시 승인            A     R      C       C       I
```

## 8. 가설 기반 개발 (Hypothesis-Driven Development)

모든 신기능은 **검증 가능한 가설**로 작성한다.

### 가설 템플릿

```
우리는 [대상 사용자]가 [기능/변경]을 경험하면
[측정 가능한 결과]가 [기준 대비 변화]할 것으로 믿는다.
우리는 [측정 방법]으로 이를 검증할 것이며
[판단 기한] 안에 [성공/실패] 여부를 결정한다.

예시:
  우리는 퀀트 분석가가 LLM Trend Analysis 기능을 경험하면
  일일 서비스 체류 시간이 기존 대비 20% 증가할 것으로 믿는다.
  우리는 Google Analytics 평균 세션 시간으로 이를 검증할 것이며
  출시 4주 안에 성공/실패 여부를 결정한다.
```

### 실험 설계 기준

| 항목 | 기준 |
|------|------|
| 최소 샘플 크기 | 통계적 유의성을 위해 최소 30명 이상 |
| 실험 기간 | 최소 2주 (단기 효과 배제) |
| 성공 지표 | 측정 가능한 수치 1~3개 (많으면 해석 어려움) |
| 실패 판단 기준 | 사전 정의 필수 (실험 후 기준 변경 금지) |

### Build-Measure-Learn 사이클

```
[Build]
  최소 기능(MVP) 구현 → 출시
        │
[Measure]
  지표 수집 (DAU, 체류시간, 오류율, NPS)
        │
[Learn]
  가설 검증 → 지속/피벗/중단 결정
        │
        ├─ 성공: 기능 확장·다음 가설
        ├─ 실패: 가설 수정·피벗
        └─ 불확실: 실험 기간 연장·데이터 추가
```

## Executable & Living Spec 연계 (Level 4+)

이 문서의 Gherkin 인수기준은 CI에서 **실제로 실행**된다 (`01.03_std_executable_specification.md` 참조).  
스펙 신선도는 `07.02_std_living_specification.md`의 Drift 체크로 자동 감지된다.

```
AC 작성 (이 문서, Gherkin 형식)
    │
    ▼ 개발자
tests/bdd/features/*.feature 파일 작성
    │
    ▼ CI (bdd-test job)
Behave / Cucumber 자동 실행
    │  실패 시 PR 머지 차단
    ▼
Spec Coverage 리포트 → PR 댓글 자동 게시
```

**스펙 신선도 경고**: 마지막 스펙 갱신 후 코드 커밋이 20건 이상 누적되면 CI 경고 발생.  
**AI Validator**: 스펙 PR 오픈 시 완전성·일관성을 AI가 자동 검증 (`09.01_std_autonomous_spec.md` 참조).
