# Enterprise Spec — API Governance (API 설계·등록·수명주기)

> 조직 전체 **API 포트폴리오 거버넌스** 표준을 정의한다.  
> 목표: 모든 API를 발견 가능하게(Discoverable), 일관되게(Consistent), 안전하게(Secure) 관리한다.

---

## API 거버넌스 프레임워크

```
[API 생산자 팀]
  API 설계 (OpenAPI 3.1)
        │
        ▼
[API Design Review]
  ├─ Spectral Linting (자동)
  ├─ Breaking Change 감지 (oasdiff)
  └─ ARB 리뷰 (중요 API)
        │
        ▼
[API Registry (Backstage / Apicurio)]
  ├─ API 카탈로그 등록
  ├─ 버전 이력 관리
  └─ 소비자 구독
        │
        ▼
[API Gateway (Kong)]
  ├─ 라우팅, 인증, Rate Limit
  └─ 트래픽 모니터링
        │
        ▼
[API 소비자 팀]
```

## API 설계 표준 (Design-First)

### OpenAPI 3.1 필수 구조

```yaml
# 모든 API는 OpenAPI 3.1 스펙으로 먼저 설계 후 구현
openapi: "3.1.0"
info:
  title: "S&P 500 Market Data API"
  version: "1.0.0"
  description: "S&P 500 일별 주가·Sector 분석 데이터 API"
  contact:
    name: "Data Platform Team"
    email: "data-platform@corp.example.com"
  license:
    name: "Internal"
  x-api-id: "sp500-market-data-v1"       # 전사 고유 ID
  x-audience: "internal"                  # internal | partner | public
  x-team: "data-platform"
  x-lifecycle: "production"              # design | development | production | deprecated | retired

servers:
  - url: "https://api.corp.example.com/sp500/v1"
    description: "Production"
  - url: "https://api-staging.corp.example.com/sp500/v1"
    description: "Staging"

tags:
  - name: ods
    description: "ODS 레이어 — 원시 종목 데이터"
  - name: dw
    description: "DW 레이어 — Sector 집계"
  - name: mart
    description: "Mart 레이어 — 지표 및 LLM 분석"
```

### URL 설계 규칙

| 항목 | 규칙 | 예시 |
|------|------|------|
| 리소스명 | 복수 명사, 소문자, 하이픈 | `/sector-aggregations`, `/key-indexes` |
| 계층 | 2단계 이하 권장 | `/sectors/{id}/metrics` |
| 버전 | URL 경로에 포함 | `/v1/`, `/v2/` |
| 필터 | Query parameter | `?trade_date=2026-05-01&sector=IT` |
| 정렬 | `sort`, `order` 파라미터 | `?sort=return_pct&order=desc` |
| 페이지네이션 | offset 또는 cursor 기반 | `?page=1&size=50` |

### HTTP 메서드 사용 기준

| 메서드 | 용도 | 멱등성 |
|--------|------|--------|
| GET | 조회 | ✅ |
| POST | 생성, 복잡한 조회(body 필요 시) | ❌ |
| PUT | 전체 교체 | ✅ |
| PATCH | 부분 업데이트 | ❌ (구현에 따라) |
| DELETE | 삭제 | ✅ |

### 응답 코드 표준

| 상황 | 코드 |
|------|------|
| 조회 성공 | 200 |
| 생성 성공 | 201 |
| 비동기 처리 수락 | 202 |
| 응답 없음 (삭제 등) | 204 |
| 잘못된 요청 | 400 |
| 인증 실패 | 401 |
| 권한 없음 | 403 |
| 리소스 없음 | 404 |
| 비즈니스 규칙 충돌 | 409 |
| Rate Limit 초과 | 429 |
| 서버 오류 | 500 |
| 의존 서비스 장애 | 503 |

### 공통 에러 포맷 (RFC 7807 Problem Details)

```json
{
  "type": "https://api.corp.example.com/errors/data-not-found",
  "title": "데이터를 찾을 수 없습니다",
  "status": 404,
  "detail": "2026-05-01 날짜의 거래 데이터가 존재하지 않습니다.",
  "instance": "/v1/ods/prices?trade_date=2026-05-01",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736"
}
```

## API Linting (Spectral)

모든 OpenAPI 스펙은 PR 생성 시 자동 Linting을 통과해야 한다.

```yaml
# .spectral.yaml
extends: ["spectral:oas", "@stoplight/spectral-owasp-rules"]
rules:
  # 필수 정보
  api-id-required:
    description: "x-api-id 필드 필수"
    given: "$.info"
    then:
      field: "x-api-id"
      function: truthy

  # 버전 포함 URL
  path-must-include-version:
    description: "API 경로에 버전 포함 필수"
    given: "$.paths[*]~"
    then:
      function: pattern
      functionOptions: { match: "^/v[0-9]+" }

  # 에러 응답 정의
  error-response-must-be-defined:
    description: "모든 엔드포인트에 400, 401, 500 응답 정의 필수"
    given: "$.paths[*][*].responses"
    then:
      function: schema
      functionOptions:
        schema:
          required: ["400", "401", "500"]
```

## Breaking Change 감지

```bash
# CI에서 PR 시 Breaking Change 자동 감지
oasdiff breaking \
  --base https://api.corp.example.com/sp500/v1/openapi.json \
  --revision ./openapi.yaml \
  --fail-on ERR    # Breaking change 발견 시 CI 실패

# Breaking change 예시 (차단됨)
# - 응답 필드 삭제
# - 필수 요청 파라미터 추가
# - 상태 코드 변경

# Non-breaking change 예시 (허용)
# - 선택 응답 필드 추가
# - 선택 요청 파라미터 추가
# - 설명(description) 수정
```

## API 수명주기 (Lifecycle)

```
design → development → production → deprecated → retired

[각 단계 전환 조건]
  design → development: 설계 리뷰 통과 (Spectral + ARB)
  development → production: 통합 테스트 통과, 보안 검토 완료
  production → deprecated: 대체 API 존재, 6개월 공지 기간
  deprecated → retired: 소비자 마이그레이션 완료 확인
```

### Deprecation 정책

```http
# 응답 헤더로 Deprecation 공지
HTTP/1.1 200 OK
Deprecation: Tue, 01 Dec 2026 00:00:00 GMT
Sunset: Wed, 01 Jun 2027 00:00:00 GMT
Link: <https://api.corp.example.com/sp500/v2>; rel="successor-version"
```

- `deprecated` 상태 전환 시 소비자 팀에 이메일 + Slack 공지
- Deprecation 기간: 최소 **6개월** (파트너 API는 12개월)
- `retired` 전환 시 응답: `410 Gone`

## API Registry

### 등록 필수 항목

| 항목 | 설명 |
|------|------|
| API ID | 전사 고유 식별자 (`x-api-id`) |
| 소유팀 | Owner 팀, Slack 채널 |
| 대상 | internal / partner / public |
| SLO | 가용성·응답시간 목표 |
| Changelog | 버전별 변경 이력 |
| 소비자 목록 | 의존 팀 목록 (Breaking Change 공지용) |

### Registry 자동화 (GitHub Actions)

```yaml
# .github/workflows/api-registry.yml
- name: Register API to Catalog
  run: |
    curl -X PUT https://api-registry.internal/apis/${{ env.API_ID }} \
      -H "Authorization: Bearer ${{ secrets.REGISTRY_TOKEN }}" \
      -H "Content-Type: application/json" \
      -d @openapi.yaml
```

## API 버전 관리 전략

| 전략 | 방법 | 권장 여부 |
|------|------|----------|
| URL 버전 | `/v1/`, `/v2/` | ✅ 권장 |
| Header 버전 | `API-Version: 2` | ⚠️ 선택적 |
| Query 버전 | `?version=2` | ❌ 비권장 |

**Major 버전 정책**:
- Major 버전 = Breaking Change 발생 시에만 증가
- 2개 이상의 Major 버전 동시 운영 금지 (비용·복잡도)
- v(N-1)은 vN 출시 후 6개월 유지 후 Sunset

## Living Spec 연계 (Level 4+) — Code-first OpenAPI

**코드가 변경되면 API 스펙이 자동으로 갱신된다** (`07.02_std_living_specification.md` 참조).

```
FastAPI / SpringDoc
    │ 코드에서 OpenAPI 자동 생성
    ▼
CI (spec-sync.yml)
    │ api_contract.md 갱신 PR 자동 생성
    ▼
리뷰어 승인 → 머지
    │
    ▼
Spectral Lint · oasdiff Drift 체크 (항상 실행)
```

- 코드가 스펙보다 앞서가는 드리프트 즉시 감지
- Breaking Change는 `oasdiff`가 PR에서 자동 차단
- API Registry에 새 버전 자동 등록
