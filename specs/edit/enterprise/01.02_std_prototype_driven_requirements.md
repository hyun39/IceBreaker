# Enterprise Spec — 프로토타입 주도 요건 진화 (Prototype-Driven Requirements)

> **핵심 관점**: 목업(Mockup)은 최종 산출물이 아니다.  
> 목업은 **불분명한 요건을 빠르게 가시화하고, 피드백으로 요건을 진화시키는 도구**다.  
> "요건 → 목업 → 피드백 → 요건 갱신"의 루프를 반복해 점진적으로 요건을 정확하게 만든다.

---

## 왜 목업으로 요건을 진화시키는가

### 전통적 방식의 문제

```
요건 문서 작성 (글)
        │  수주~수개월 후
        ▼
개발 완료
        │
        ▼
"이게 아닌데요..."  ← 이 순간 비용이 가장 크다
```

말과 글로만 요건을 정의하면 **이해관계자마다 다르게 상상**한다.  
개발이 끝난 후에 "이게 아닌데요"는 재작업 비용이 10~100배로 뛴다.

### 목업 주도 방식의 핵심

```
흐릿한 아이디어
        │  목업(L0)으로 빠르게 가시화
        ▼
팀이 같은 것을 보며 토론 → 요건 갱신
        │  더 구체적인 목업(L1)으로
        ▼
사용자 반응 관찰 → 요건 갱신
        │  실제 데이터와 인터랙션(L2/L3)으로
        ▼
"맞아요, 이거예요" → 개발 착수
```

**목업 1개 = 1,000 단어짜리 요건 문서**보다 더 많은 것을 전달한다.

---

## 요건 진화 모델 (Requirements Evolution Model)

### 진화 사이클

```
            ┌──────────────────────────────────────┐
            │                                      │
    [흐릿한 아이디어·가설]                          │ (반복)
            │                                      │
            ▼                                      │
    [목업 생성] ─── AI 자동화 (L1/L2)              │
            │                                      │
            ▼                                      │
    [관찰·피드백 수집]                             │
      ├─ 사용자: 어디서 멈추는가?                  │
      ├─ 이해관계자: 우선순위가 맞는가?            │
      └─ 개발팀: 구현 가능한가?                    │
            │                                      │
            ▼                                      │
    [요건 갱신]                                     │
      ├─ 유저스토리 수정·추가·삭제                 │
      ├─ 인수 기준 구체화                          │
      └─ 우선순위 재조정                           │
            │                                      │
            ▼                                      │
    [충분히 검증됐는가?]                            │
      ├─ No  ─────────────────────────────────────┘
      └─ Yes → DoR 통과 → 개발 착수
```

## 목업 레벨과 요건 진화 단계 대응

각 레벨에서 **어떤 요건이 진화하는지** 명시한다.

### L0 — 종이·화이트보드 (30분~1시간)

**진화하는 요건**: 비즈니스 가설 수준의 "무엇을"

```
입력: 흐릿한 아이디어 ("Sector 트렌드를 보고 싶다")
        │
        ▼ L0 목업
출력: 진화된 요건 예시
  - 어떤 화면이 필요한가? (ODS탭·DW탭·Mart탭)
  - 핵심 흐름이 무엇인가? (날짜선택 → Sector필터 → 결과확인)
  - 무엇이 가장 중요한가? (트렌드 요약 카드 > 원시 데이터)
```

**도구**: 포스트잇, 화이트보드, Miro  
**피드백 방법**: 팀 5분 워크샷 투표 (Dot Voting)  
**산출물**: 화면 목록 초안 + 우선순위 순서

---

### L1 — React Skeleton (구조·계층 검증, 0.5~1일)

**진화하는 요건**: 정보 구조·네비게이션·화면 흐름

```
입력: L0 화면 목록 + 유저스토리 초안
        │
        ▼ AI 자동 생성 (parse_spec.py → gen_l1_skeleton.py)
출력: 회색 박스 React 컴포넌트 → Storybook
        │
        ▼ 팀 리뷰 (Chromatic PR Preview)
진화하는 요건:
  - "날짜 선택기가 상단에 있어야 하는가, 사이드에 있어야 하는가?"
  - "ODS 탭이 기본 탭이어야 하는가?"
  - "Sector 필터가 페이지 진입 시 필요한가, 결과 화면에서 필요한가?"
  - "한 화면에 ODS+DW를 모두 보여줄 수 있는가?"
```

**피드백 방법**: Chromatic 댓글 비동기 리뷰  
**산출물**: 정보 구조 확정 + 유저스토리 정제

---

### L2 — React Hi-fi (실제 컴포넌트·데이터 모양 검증, 3~5일)

**진화하는 요건**: 데이터 표현 방식·상태 정의·예외 처리

```
입력: 확정된 정보 구조 + api_contract.md 초안
        │
        ▼ AI 자동 생성 (gen_l2_hifi.py + gen_msw_handlers.py)
출력: @corp/design-system 컴포넌트 + MSW 목업 데이터
        │
        ▼ 이해관계자 데모 + 게릴라 테스트 (3~5명)
진화하는 요건:
  ✅ 확정: "RSI 62는 '과매수 주의' 배지로 표시한다"
  ✅ 확정: "비거래일은 가장 최근 거래일 자동 선택한다"
  ❌ 제거: "거래량 히스토그램은 필요 없다" (사용자 무관심)
  ➕ 추가: "LLM 분석 중일 때 Skeleton 로딩을 보여줘야 한다"
  ➕ 추가: "면책문구는 항상 하단에 고정되어야 한다"
```

**피드백 방법**: 게릴라 테스트 (발화 사고, 30분 × 3~5명)  
**산출물**: 확정 유저스토리 + Gherkin 인수 기준 + API 계약 v1

---

### L3 — Interactive Coded Mockup (실 인터랙션 검증, 5~10일)

**진화하는 요건**: 엣지 케이스·성능 체감·API 계약 세부

```
입력: 확정 인수 기준 + api_contract.md v1
        │
        ▼ MSW 핸들러 + 실 시나리오 구현
출력: 완전한 인터랙티브 목업 (실데이터 모양, 로딩/에러/빈 상태)
        │
        ▼ 확장된 사용성 테스트 (5~8명)
진화하는 요건:
  ✅ 확정: "폴링 간격은 30초가 적절하다"
  ✅ 확정: "500개 종목 테이블은 50행 페이지네이션이 충분하다"
  ❌ 제거: "실시간 차트 애니메이션" (성능·비용 부담)
  ➕ 추가: "비거래일 접속 시 배너로 명확히 알린다"
```

**피드백 방법**: 확장 사용성 테스트 + 이해관계자 UAT  
**산출물**: 최종 확정 요건 + DoR 통과 준비 완료

## AI 자동화 파이프라인 상세

### 핵심 원칙

> **목업은 버리지 않는다.**  
> 동일한 기술 스택(React + @corp/design-system)으로 만들기 때문에  
> L2/L3에서 검증된 컴포넌트는 프로덕션 코드로 그대로 이식된다.

### `parse_spec.py` — 요건에서 화면을 추출하는 핵심

이 스크립트가 **"요건이 어떤 화면과 상태를 요구하는가"**를 자동으로 도출한다.

```python
PARSE_SYSTEM = """
당신은 비즈니스 요건 분석 전문가입니다.
유저스토리와 인수기준(Gherkin)을 분석해 UI 화면 설계 정보를 추출합니다.

핵심 규칙:
- 시나리오의 각 단계(When/Then)는 화면 상태로 변환됩니다
- 인수기준의 예외(But/And Error) 는 error_cases로 추출됩니다
- 빠진 상태(loading/empty)는 자동으로 추가됩니다
- API 엔드포인트는 인수기준의 데이터 참조에서 유추합니다
"""

PARSE_PROMPT = """
비즈니스 스펙:
{spec_content}

다음 JSON으로 변환하라:
{{
  "feature_name": "snake_case",
  "requirement_version": "v{날짜}",  // 요건 버전 추적
  "screens": [
    {{
      "id": "screen_ods",
      "name": "ODS 종목 조회",
      "user_story_refs": ["US-001", "US-002"],  // 근거 유저스토리
      "acceptance_criteria_refs": ["AC-001-01"],  // 근거 인수기준
      "components": [...],
      "states": ["loading", "success", "empty", "error"],
      "error_cases": ["비거래일", "데이터 없음"],
      "open_questions": [  // 요건이 불명확한 부분 자동 탐지
        "거래량 단위가 주식 수인가, 달러인가?"
      ]
    }}
  ]
}}
"""
```

> **`open_questions` 필드**: LLM이 요건 파싱 중 발견한 **불명확한 요건을 자동으로 리스트업**한다.  
> PR 댓글에 포함되어 팀이 즉시 논의하도록 유도한다.

### `gen_l1_skeleton.py` — 레이아웃으로 정보 구조 검증

```python
L1_SYSTEM = """
Lo-fi Skeleton React 컴포넌트를 생성합니다.
규칙:
- 모든 UI 요소는 회색 박스 (div + Tailwind bg-gray-*)로 대체
- 텍스트는 설명 레이블만 ("날짜 선택기", "Sector 필터", "결과 테이블")
- 실제 컴포넌트, 실제 색상 사용 금지
- 레이아웃·계층·흐름만 표현 — 디자인 판단은 사람이 함

목적:
이 컴포넌트를 보고 팀이 답해야 하는 질문:
1. 정보의 우선순위가 레이아웃에 반영됐는가?
2. 네비게이션 흐름이 자연스러운가?
3. 빠진 화면이나 상태가 있는가?
"""
```

**L1 생성 예시**:

```tsx
// 자동 생성된 L1 Skeleton
export function OdsScreenL1({ state = 'success' }: { state: ComponentState }) {
  return (
    <div className="flex flex-col h-full">
      {/* 헤더 영역 */}
      <div className="flex gap-2 p-4 border-b">
        <div className="h-9 w-40 bg-gray-200 rounded" title="날짜 선택기" />
        <div className="h-9 w-32 bg-gray-200 rounded" title="Sector 필터" />
      </div>

      {/* 탭 영역 */}
      <div className="flex gap-1 px-4 pt-3">
        {['ODS', 'DW', 'Mart-Index', 'Mart-Trend'].map(tab => (
          <div key={tab} className="h-8 w-24 bg-gray-200 rounded-t" title={tab} />
        ))}
      </div>

      {/* 콘텐츠 영역 */}
      {state === 'loading' && (
        <div className="flex-1 m-4 bg-gray-100 rounded animate-pulse" title="로딩 중" />
      )}
      {state === 'success' && (
        <div className="flex-1 m-4 bg-gray-100 rounded border-2 border-dashed border-gray-300
                        flex items-center justify-center text-gray-400 text-sm">
          종목별 가격 테이블 (예: 50행 × 8컬럼)
        </div>
      )}
      {state === 'empty' && (
        <div className="flex-1 m-4 flex items-center justify-center text-gray-400">
          데이터 없음 안내
        </div>
      )}
      {state === 'error' && (
        <div className="flex-1 m-4 bg-red-50 rounded border border-red-200
                        flex items-center justify-center text-red-400 text-sm">
          에러 상태 안내
        </div>
      )}
    </div>
  );
}
```


### MSW — 요건의 "엣지 케이스"를 코드로 표현

MSW 핸들러는 단순한 가짜 API가 아니라 **요건의 예외 케이스를 코드로 표현한 것**이다.

```typescript
// gen_msw_handlers.py가 생성하는 핸들러 — 요건 예외를 시뮬레이션

export const handlers = [
  // 정상 케이스: FR-05 "거래일 데이터 표시"
  http.get('/api/v1/ods/prices', ({ request }) => {
    const url = new URL(request.url);
    const date = url.searchParams.get('trade_date');

    // 예외 케이스: FR-08 "비거래일 처리"  ← 요건이 코드로 표현됨
    if (isWeekend(date) || isHoliday(date)) {
      return HttpResponse.json(
        { error: { code: 'NON_TRADING_DAY', message: '비거래일입니다.' } },
        { status: 404 }
      );
    }

    // 예외 케이스: 빈 데이터  ← FR-X "빈 상태 처리"
    if (date < '2020-01-01') {
      return HttpResponse.json({ trade_date: date, items: [], pagination: { total: 0 } });
    }

    return HttpResponse.json(odsFixture);
  }),

  // LLM 분석 진행 중: FR-07 "분석 중 상태 표시"
  http.get('/api/v1/mart/trend-analysis', async () => {
    await delay(1500);  // 실제 LLM 지연 시뮬레이션
    return HttpResponse.json({
      is_complete: false,
      completed_sectors: 7,
      total_sectors: 11,
    });
  }),
];
```

## 요건 검증 결정 기준 (언제 다음 레벨로 가는가)

| 현재 레벨 | 다음 레벨 진행 조건 | 재작업 조건 |
|---------|----------------|-----------|
| L0 → L1 | 화면 목록·흐름에 팀 합의 | 핵심 화면 누락 또는 흐름 이견 |
| L1 → L2 | 정보 구조·네비게이션 팀 승인 | Critical 피드백 존재 |
| L2 → L3 | 이해관계자 승인 + 게릴라 테스트 Critical 0건 | Critical/Major 피드백 존재 |
| L3 → 개발 | DoR 전체 통과 + 요건 변경 이력 안정화 | 기능 범위 불확실성 > 20% |

### 요건 안정화 신호 (개발 착수 OK)

```
✅ 연속 2회 테스트에서 신규 Critical 피드백 0건
✅ 유저스토리 추가·삭제가 최근 1주 없음
✅ open_questions 모두 해소됨
✅ API 계약 (api_contract.md) v1 확정
✅ 이해관계자 서명 승인 완료
```

### 요건 불안정 신호 (계속 목업으로 진화)

```
⚠️ 테스트마다 새로운 Critical 피드백
⚠️ "이 화면이 진짜 필요한가?" 질문이 반복됨
⚠️ 이해관계자마다 다른 방향을 원함
⚠️ open_questions 해소 속도 < 생성 속도
```

## 반복 횟수 가이드라인

| 불확실성 수준 | 예상 목업 반복 | 비고 |
|------------|------------|------|
| 낮음 (명확한 요건) | 1~2회 | L1 → 바로 DoR |
| 중간 (일부 불명확) | 3~5회 | L1 → L2 → L3 |
| 높음 (가설 수준) | 5~10회 | L0 → L1 여러 번 → L2 → L3 |
| 매우 높음 (신규 도메인) | 10회+ | 스파이크(Spike) 또는 별도 Discovery Sprint |

> **"빠른 실패가 올바른 실패다"**: 1주 목업 반복 10번이 3개월 개발 후 재작업보다 낫다.
